# 个人知识图谱产品需求文档

版本：0.2 草案  
日期：2026-10-27  
状态：供需求讨论和修改，尚未进入实现

这个项目用于维护你自己添加的知识，以 Markdown 保存知识内容，以图保存知识之间的关联，并在可自由穿梭的三维点云中呈现。你可以向应用里的 AI 询问知识之间的联系，AI 根据你的回答整理关系，在你确认后保存。

首版建议采用单人使用、桌面浏览器优先的 Web 应用，以 PostgreSQL 加 pgvector 保存内容、关系和语义向量。算法负责发现云团和生成配色，你负责决定哪些联系成为正式知识关系。

## 1 产品边界和需求依据

### 1.1 已明确的需求

| 编号 | 需求 |
| --- | --- |
| R01 | 项目转向个人知识图谱，重建时清除旧产品内容 |
| R02 | 知识点由你自己添加 |
| R03 | 知识点之间通过图结构表达关联 |
| R04 | 可以询问 AI 知识点之间的关联，并根据你的回复建立连接 |
| R05 | 应用内有大模型入口配置 |
| R06 | 每个知识点有可展开阅读的 Markdown 内容 |
| R07 | 不同领域形成点状云团，云团有不同颜色 |
| R08 | 云团归属和颜色通过计算产生，而非仅手工分类 |
| R09 | 可以在三维空间自由穿梭、缩放、进入知识内容 |
| R10 | 录入采用主流 AI 工作流框架，依次解析、匹配现有知识、推荐关联、用户确认或修改，最后加入图谱 |

### 1.2 首版建议和待确认假设

- 单人知识库、桌面浏览器优先；部署方式暂按本机启动服务设计。
- 大模型对话发生在项目应用内；通过聊天窗口确认的关系持久化到该应用。
- AI 可以建议补充知识，但不能自行创建正式知识点或改写你的正文。
- Markdown 以数据库正文为主，支持导入导出 `.md`；是否直接维护本地 Markdown 文件夹待确认。
- 关系写入需要明确确认。你回复“按这个关系连接”可直接视为确认，无须重复点击。
- 首版保留手动连线能力，在模型不可用时仍可维护图谱。

旧方案中的学习挑战、测评、排行榜、社交分享、收款和公开知识库均不进入本次范围。产品名称暂用“个人知识图谱”。

### 1.3 本轮交付和重建范围

本轮只新增需求文档，保留现有文件，便于讨论调整。进入重建阶段后，清理旧业务代码、旧产品文档、演示原型和构建产物，改写项目说明与依赖；保留 Git 历史和必要的项目配置。旧原型中的交互想法可以参考，其演示节点不导入你的知识库。

## 2 核心使用流程

### 2.1 通过工作流录入知识

录入分为草稿和正式入图两个阶段。保存草稿不会立即生成正式图谱节点；必须经过解析、匹配、关联建议和用户审阅，才能提交加入图谱。

```text
输入标题和 Markdown，保存草稿
              ↓
解析知识点：概念、摘要、别名、主题、歧义
              ↓
匹配空间中已有知识：语义检索、关键词、已有关系上下文
              ↓
给出关联建议：目标节点、关系类型、方向、依据
              ↓
用户审阅：接受、拒绝、修改、手动补充
       ↖ 内容变化后重新分析
              ↓ 明确确认加入图谱
校验并保存知识点和已确认关系
              ↓
后台更新云团、颜色和位置，镜头定位新节点
```

“空间中已有知识”指当前知识库的正式节点，匹配不依赖镜头位置或屏幕上是否可见。三维距离不作为内容匹配分数。

每一步显示当前状态和可检查的结果。你可以退出后继续处理草稿；刷新页面或服务重启后，可以恢复等待确认的流程。无合适关联时，可明确选择“作为独立知识点加入”，不强迫连线。

### 2.2 通过对话建立关系

以已有的“梯度下降”和“反向传播”为例：

1. 你问：“这两个知识点之间有什么联系？”
2. 系统定位对应节点；存在同名节点时，先让你选择具体对象。
3. AI 读取相关正文和已有关系，区分“图谱里已记录的关系”和“模型提出的解释”。
4. AI 提出关系草案和必要追问，例如：“是否将反向传播计算的梯度用于梯度下降更新参数，作为两者的联系？”
5. 你补充：“可以，标记为用于优化，说明中保留它们不是同一个过程。”
6. 系统展示准确的起点、终点、关系类型、方向和说明；若你的回复已经明确了这些信息并授权连接，直接保存并给出结果。
7. 星图突出显示新增连线，你可撤销；确认记录与该次对话关联保存。

你只问“为什么有联系”或回复“我还没理解”时，不视为同意写入。你回复“没有关系”时保留拒绝记录，避免反复推荐同一条未变化的候选。

### 2.3 沿图谱探索

搜索一个知识点 → 镜头定位 → 展开一跳或两跳邻居 → 点击关联节点或路径 → 阅读 Markdown → 继续向 AI 追问。

“A 和 B 已经怎样连接”查询已确认图谱；“A 和 B 可能有哪些联系”可生成候选解释。系统必须清楚标明两类结果。

优先级：P0 为首版必须，P1 为后续增强。

### 3.1 知识点和 Markdown

- 一个知识点对应一个稳定 ID，标题改名不影响关系。
- 标题必填，正文可暂空；同名只提示，不自动合并。
- 新录入先保存草稿，通过第 3.5 节工作流确认后才成为正式节点。正文为空或信息不足时，允许补充内容，或在人工审阅后作为独立节点加入。
- 正文可在右侧面板展开，也可进入完整阅读与编辑视图。
- 编辑时显示“未保存／保存中／已保存／失败”；正文切换前处理未保存内容。
- 标题或正文修改后，原有向量标记为过期并后台更新；旧任务不得覆盖新版本结果。
- 删除知识点时展示关联数量，软删除节点及其关系；恢复时检查端点有效性。
- Markdown 中的普通链接不自动变成知识关系；未来可增加显式知识引用语法。

### 3.2 关系定义

关系是一条带属性的边。两个知识点之间允许存在不同类型的关系，支持跨云团连接和环路，不强制构成树。

| 类型 | 含义及方向 |
| --- | --- |
| 相关 | A 与 B 相关，对称关系 |
| 前置于 | A 是学习或理解 B 的前提，A → B |
| 属于 | A 是 B 的组成部分或子类，A → B；说明中写清具体含义 |
| 用于 | A 用于 B，A → B |
| 对比 | A 与 B 值得对照理解，对称关系 |

“前置于”属于解释学习顺序的关系，保存时若形成循环需提示核查；普通“相关”关系允许成环。界面用箭头或明确的文字解释方向。

相同端点、类型和方向的正式关系不重复插入；更新说明时保留历史。对称关系对端点顺序标准化。默认禁止自己连接自己。

### 3.3 AI 查询和写入规则

- 先检索你的知识库，再回答；引用可点击回到知识点正文。超出已有内容的模型解释标为推测，不能伪装成已有记录。
- 草案必须绑定真实节点 ID，缺失知识点时提示你新建，不使用虚构端点。
- 一个回答包含多条候选关系时，允许逐条接受、修改或拒绝。
- 未确认草案不参与正式图查询，也不显示成正式连线。
- 关系状态为：候选 → 待澄清 → 已确认／已拒绝／已取消；已确认关系的后续修改另存历史。
- 确认前若相关正文已更新、节点已删除或关系已改变，应重新校验并让你复核变化。
- 重试、刷新或重复点击不得重复建边；一组确认操作应以事务保存。
- 模型故障、超时或返回格式错误时保留对话与草案，不写入半成品关系。

### 3.4 大模型配置入口

设置页分别配置“对话模型”和“向量模型”。对话模型用于问答、澄清和关系草案；向量模型把正文转换成可计算相似度的表示。两者可来自不同服务。

| 字段或操作 | 要求 |
| --- | --- |
| 服务配置 | 名称、协议适配器、Base URL、API Key、模型 ID |
| 对话参数 | 超时、输出长度；高级参数可折叠 |
| 向量参数 | 模型 ID、输出维度、分段规则和版本 |
| 测试连接 | 分别验证对话与向量请求，显示可理解的失败原因 |
| 切换向量模型 | 提示需要重建向量索引；新索引完成后统一切换 |
| 无模型状态 | 可维护正文、手工连线和浏览已有图；AI 与语义聚类显示未配置 |

首版建议支持 OpenAI 兼容接口作为通用适配方式，具体服务是否兼容以连接测试为准。模型调用由后端完成，密钥不写入前端代码、普通日志或知识库导出包。页面保存后只显示脱敏值。向外部模型发送内容前，设置页说明发送范围；按问题只选取必要正文，不默认上传整个知识库。

### 3.5 知识录入 AI 工作流

#### 框架选型

采用 **LangGraph，使用 TypeScript 版本**作为录入流程的编排框架，模型调用和检索可使用 LangChain 生态组件。LangGraph 支持确定性步骤与模型步骤组合，适合在同一流程中安排解析、检索、人工审阅和数据库写入，参见 [LangGraph 官方概览](https://docs.langchain.com/oss/javascript/langgraph/overview)。

采用主流框架，避免自建工作流引擎。“世界最常用”缺少统一的实际使用量统计口径，不以此作为未经验证的排名结论；当前选型依据为流程能力、生态和 TypeScript 集成适配性。

人工审阅使用 LangGraph 的中断与恢复机制，状态使用持久化检查点保存，参见 [人工中断文档](https://docs.langchain.com/oss/javascript/langgraph/interrupts)和[持久化文档](https://docs.langchain.com/oss/javascript/langgraph/persistence)。首版使用代码定义固定工作流，在产品中展示进度与结果；拖拽式工作流编辑器属于后续扩展。

#### 五个业务步骤

| 步骤 | 处理内容 | 用户可见结果 |
| --- | --- | --- |
| 1 解析知识点 | 保留原文，提取核心概念、摘要、别名、候选主题和歧义；若包含多个独立概念，提出拆分建议 | 解析卡片，可修改；AI 不直接覆盖正文或自动拆成多个正式节点 |
| 2 分析匹配程度 | 对当前草稿生成向量，全库召回语义与关键词候选，结合候选正文和已有关系进行重排 | 匹配列表：节点标题、匹配等级、相关段落、相似或差异原因；提示疑似重复 |
| 3 给出关联建议 | 对候选判断是否适合连线，输出起终点、关系类型、方向、说明和依据；允许跨云团推荐 | 可逐条审阅的关联卡片，可在空间中预览临时节点及虚线 |
| 4 用户确认或修改 | 接受、拒绝、修改类型与方向、补充说明、搜索其他节点手动加关联，或修改解析和原文 | 待提交清单，明确列出最终知识内容和即将创建的关系 |
| 5 加入知识图谱 | 校验目标节点与内容版本，事务保存新节点、确认关系和确认来源，完成后触发空间更新 | 入图成功，定位新节点、突出新增连线，支持撤销本次入图 |

#### 匹配和建议的解释要求

- 召回先使用相似度过滤与数量上限，随后模型只分析候选相关内容；不向模型发送全库正文。
- 页面区分“内容匹配程度”和“是否建议建立关系”。高相似度可能表示重复，低相似度也可能存在有价值的跨领域关系。
- 匹配程度首版以高、中、低等级展示，并附依据；向量余弦值可供展开查看，不把它包装成正确率或概率。等级阈值用真实样本校准。
- 每条建议引用草稿和目标节点的相关段落；依据不足的推测标明待核实。
- 首版默认展示最多 10 个匹配候选和 5 条关联建议，允许主动查看更多或手动搜索补充。这是初始产品参数，可根据实际使用调整。
- 疑似重复时允许返回修改、打开已有知识点进行编辑，或明确选择独立新增；不自动合并。
- 空库或没有合适候选时，显示原因，并允许你确认作为独立节点入图。

#### 修改和恢复规则

- 修改正文、核心概念或别名后，标记旧分析和旧确认过期，从受影响的步骤重新计算并再次审阅；不沿用对旧内容的确认。
- 仅修改某条关系类型、方向或说明时，校验该条关系即可，不必重新运行全部解析。可通过对话修改，也可直接编辑关联卡片。
- 每次运行有独立运行 ID、草稿版本、工作流版本和检查点；保存候选节点版本、模型配置引用、分析结果和用户决定。运行状态不保存 API Key。
- 工作流状态为：草稿 → 解析中 → 匹配中 → 生成建议 → 待确认 → 提交中 → 已入图；另有失败、已取消和待重新分析状态。
- 等待确认时持久化暂停，不持续占用模型调用；恢复时使用同一运行上下文，并重新检查目标节点是否仍有效。
- 中断恢复可能重执行当前步骤，数据库写入置于确认后的独立步骤，通过运行 ID 和提交操作 ID 保证幂等；不能仅依赖工作流框架防止重复写入。
- 未提交的草稿和临时连线不参与正式图查询、聚类或节点计数。
- 模型不可用时，草稿可保留并稍后重试；也可选择人工录入模式，手动选择或放弃关联，经确认后执行同样的入图校验。
- 入图成功但聚类失败时，知识与关系已经保存，节点显示“待归类”，只重试空间计算。提交结果不明确时先查询提交记录，避免重复生成节点。
- 撤销本次入图通过记录反向操作实现；若节点已被后续操作引用，先展示影响范围，不直接删除后续数据。

#### 录入界面

录入页面以“解析 → 匹配 → 建议 → 确认 → 入图”步骤条展示进度。左侧保留原始 Markdown 和解析结果，中间显示候选及关系卡片，右侧可展开空间预览。最后的“确认加入图谱”区域展示节点标题、正文版本和已选关系数量；等待模型和等待用户分别标明，可保存退出后继续。

## 4 三维空间和阅读体验

### 4.1 页面组成

- 中央：三维点云与图谱。
- 左侧可收起导航：搜索、知识列表、云团图例、筛选。
- 右侧：知识详情与 Markdown 阅读编辑。
- 独立可切换面板：AI 对话、候选关系和确认结果。
- 顶部或角落：新建知识点、设置、返回全景、聚类更新状态。

正文与 AI 面板支持切换或调整宽度，避免三维场景把阅读区域挤得过小。

### 4.2 导航规则

| 操作 | 交互 |
| --- | --- |
| 观察云团 | 鼠标拖动旋转，右键或组合键拖动平移 |
| 放大缩小 | 滚轮或触控板缩放，限制极端距离 |
| 自由穿梭 | 显式进入飞行模式，WASD 移动，QE 上下，鼠标控制朝向，速度可调 |
| 退出飞行 | Esc 退出并释放鼠标控制 |
| 查看节点 | 悬停显示标题；单击选中并打开正文面板 |
| 镜头定位 | 双击节点或使用“聚焦”；点击云团图例定位云团 |
| 防止迷路 | 返回全景、上一个视点、当前选中节点提示 |

在编辑器、搜索框或聊天输入框内打字时，不响应飞行快捷键。支持关闭镜头动画；关闭正文后恢复之前的视点和筛选状态。

### 4.3 视觉编码

- 节点代表知识点，基础大小首版保持统一，选中时使用描边或光环。
- 颜色代表算法生成的云团；名称和图例同时提供识别线索。
- 连线代表已确认关系，跨领域关系可以跨云团显示。
- 候选关系只在审阅时用虚线显示，且有“待确认”文字。
- 远景显示云团及少量标题，近景展开节点；默认只突出当前节点的邻边，减少线条遮挡。
- 三维距离是探索布局，不作为“知识关联强弱”的精确度量。
- WebGL 不可用或设备性能不足时，仍可通过列表完成搜索、正文阅读和关系维护。

## 5 云团聚类和颜色计算

### 5.1 区分领域和算法云团

你填写的标签描述主观分类，算法云团描述内容相似性。首版以算法云团作为颜色依据，手动标签用于筛选；算法结果可能与传统学科边界不同。

例如，“线性代数”可能同时靠近数学与机器学习内容，不能仅凭算法颜色断言它只属于一个学科。首版给每个节点一个主要云团，详情可展示其他相近云团；多重归属可后续扩展。

### 5.2 建议计算流程

```text
标题和 Markdown 正文
        ↓ 分段、生成向量并汇总为节点表示
语义向量
        ↓ 余弦相似度、近邻数量上限与最低相似度过滤
稀疏相似度网络（计算产物）
        ↓ Leiden 社区发现
云团成员、云团中心、稳定标识
        ↓ 与旧云团匹配并计算可区分颜色
云团颜色 + 三维布局缓存
```

选择 Leiden 作为首版待验证方案，因为它可从相似度网络中发现群组，不要求预先指定固定云团数量；群组数量仍会受分辨率等参数影响。官方实现参见 [igraph 社区发现文档](https://python.igraph.org/en/latest/api/igraph.community.html)。

相似度网络中的边只用于计算，不写入正式知识关系。这让还没手动连线的节点也能聚成云团。确认关系可以影响可视布局，但首版不直接混入语义聚类权重，以免“有关系”被等同于“内容属于同一领域”。

### 5.3 小样本和失败处理

- 空库：显示新建入口，不展示伪造知识。
- 仅一个节点：显示单点或单节点云团。
- 内容过少、低相似度孤立节点：保留为独立节点或“待归类”，不强行归入最近云团。
- 向量服务不可用：继续使用上次成功结果，新节点显示待归类。
- 内容分段后保留段落向量用于检索；聚类使用节点级汇总向量，效果需用你的实际知识样本评估。

### 5.4 颜色和位置稳定性

算法决定云团成员，颜色映射算法决定各团颜色；颜色本身不承载学科真伪或知识价值。

1. 初次计算时在感知较均匀的颜色空间生成候选色，优先让空间相邻云团具有较大色差，并检查背景对比度。
2. 更新聚类时按成员重叠匹配新旧云团，保留匹配成功云团的 ID 和颜色，避免少量新增知识使全图换色。
3. 云团合并或拆分时显示变化提示；重算结果完成后整体发布，保留上次成功快照。
4. 云团数量超出可辨识色彩范围时，结合名称、筛选、局部显示辅助区分，不承诺无限数量颜色都能清晰辨别。
5. 三维布局采用云团中心布局加团内布局，保存随机种子、坐标和布局版本；局部更新尽量保留旧位置，提供主动“重新整理布局”入口。

首版可设置“自动更新聚类”开关和“重新计算”操作。计算在后台完成，不阻塞正文保存或阅读。

## 6 数据库和数据结构建议

### 6.1 推荐 PostgreSQL 加 pgvector

知识图谱首先是一种数据模型，不必以专用图数据库起步。首版建议在 PostgreSQL 中使用节点表和边表表示图，同时保存 Markdown、对话与版本；pgvector 保存向量并执行相似度查询。

PostgreSQL 的递归查询可支持限定深度的关系遍历，参见 [官方递归查询文档](https://www.postgresql.org/docs/current/queries-with.html)。pgvector 支持精确和近似向量近邻检索，参见 [项目官方文档](https://github.com/pgvector/pgvector)。这些能力能覆盖首版的数据需求；实际性能仍需在目标数据规模上验证。

| 方案 | 适用情况 | 本项目取舍 |
| --- | --- | --- |
| PostgreSQL 加 pgvector | 统一维护正文、图关系、向量和事务 | 首版推荐；本机使用需要运行数据库服务 |
| SQLite 加向量扩展 | 强调单机安装、单文件备份、离线桌面应用 | 若你优先要求免数据库服务，应重新评估为首选 |
| Neo4j | 复杂多跳图模式查询成为主要负载 | 暂不引入第二套数据存储；后续以查询瓶颈决定是否迁移 |
| 独立向量数据库 | 大规模向量检索成为主要负载 | 首版不额外部署；它本身不能代替正文与确认记录存储 |

### 6.2 核心实体

以下为逻辑模型，正式建表时补充约束、索引和迁移脚本。

| 实体 | 关键字段 | 用途 |
| --- | --- | --- |
| knowledge_nodes | id、title、aliases、markdown、tags、sources、revision、created_at、updated_at、deleted_at | 知识点正文与元数据 |
| knowledge_drafts | id、title、markdown、aliases、tags、revision、status、created_at、updated_at | 待入图草稿，与正式节点隔离 |
| ingestion_runs | id、draft_id、draft_revision、workflow_version、thread_id、stage、status、分析结果、候选版本、提交操作 ID、result_node_id | 录入工作流及业务状态 |
| workflow_checkpoints | thread_id、checkpoint_id、工作流状态、保存时间 | 由 LangGraph 持久化适配器管理，支持暂停和恢复 |
| node_revisions | node_id、revision、正文快照、变更时间 | 内容历史与恢复 |
| relations | id、source_id、target_id、type、description、confirmation_id、revision、deleted_at | 已确认正式关系 |
| relation_proposals | id、conversation_id 或 ingestion_run_id、source_draft_id 或 source_node_id、target_node_id、类型、方向、说明、端点版本、status | 录入及对话中的候选、拒绝和确认过程；入图时解析为正式端点 |
| relation_events | relation_id、operation、before、after、confirmation_id、时间 | 关系修改与撤销记录 |
| conversations 和 messages | id、role、content、引用节点、时间 | 问答记录与用户确认原文 |
| confirmations | id、来源类型、message_id 或 ingestion_run_id、草稿版本、proposal_ids、决定快照、操作唯一标识、时间 | 将对话回复或界面确认绑定到准确的写入动作 |
| embeddings | node_id、chunk_id、文本范围、vector、model_id、dimension、content_revision、index_version | 节点与段落语义表示 |
| cluster_runs 和 clusters | run_id、算法参数、输入版本、status、cluster_id、label、color、center | 聚类快照和云团 |
| cluster_memberships | run_id、cluster_id、node_id | 每次计算的成员归属 |
| layout_positions | node_id、layout_version、x、y、z、pinned | 可重建的空间坐标 |
| model_profiles | id、用途、adapter、base_url、model_id、secret_ref、参数 | 模型配置；密钥独立存储 |
| jobs | id、type、输入版本、status、error、retry_count | 向量、聚类与布局任务 |

正式图结构为带类型和属性的图：节点是知识点，有向边表达方向关系，对称边通过规则标准化。端点加外键，邻居查询使用 source_id 和 target_id 索引。多跳查询设置跳数、返回数量与超时限制，并处理环路；“没查到路径”需注明搜索范围，不能直接等同于不存在关联。

向量、云团和坐标是可重建的计算结果；正文、正式关系、确认来源和内容历史是核心资产。不同模型或维度的向量分开建索引，不直接混合比较。

### 6.3 Markdown 存储和导出

首版建议数据库中的 Markdown 是唯一正文来源，避免“数据库一份、本地文件一份”双向同步冲突。阅读正文就是读取该节点 Markdown，不依赖文件名定位关系。

- 单篇导出：标题、稳定 ID、别名和标签写入 front matter，正文保留 Markdown。
- 完整导出：Markdown 文件、关系 JSON、对话与确认记录、版本和清单；云团坐标可选。
- 单独导入 `.md`：只导入知识点，不根据普通链接自动造关系。
- 完整恢复：按稳定 ID 恢复节点和边，校验引用；冲突先预览，不能静默覆盖。
- 密钥不进入普通导出。完整备份必须能恢复已确认关系及其方向，不能仅备份 Markdown。

如果你希望直接在 IDE 编辑每一篇 `.md`，需要把“文件夹作为正文来源”和同步冲突处理提升为首版需求，此时应调整上述方案。

## 7 系统协作和异常处理

建议架构为：浏览器三维场景与编辑器 → 应用后端 → PostgreSQL 加 pgvector；后端调用模型服务，后台任务计算向量、聚类与布局。三维层可采用 Three.js，具体框架在需求确定后选择。

- 后端用 LangGraph 编排录入工作流，PostgreSQL 同时保存业务数据和工作流检查点；检查点不能代替正式节点与关系记录。
- 草稿保存不等待模型处理，正式添加在人工确认和事务提交后完成；入图后的聚类与布局异步执行。
- 后台按内容版本执行，旧任务完成时检查版本，避免覆盖新内容。
- 未配置向量模型时，提供中性点云与已有布局，不把随机配色伪装成计算分类。
- Markdown 渲染过滤不安全 HTML，链接按安全规则打开。
- 本机部署默认仅本机访问；如果需要公网访问，再补充登录、权限和服务端密钥保护方案。

## 8 首版验收标准

| 场景 | 通过标准 |
| --- | --- |
| 添加知识 | 草稿经过解析、匹配、建议和用户确认后，正式节点与已选关系一起保存；刷新和重启后仍能读取 |
| 工作流恢复 | 在待确认时刷新或重启，能恢复原草稿及审阅结果；取消不会生成正式节点 |
| 匹配建议 | 检索覆盖全库，不受镜头位置限制；每条建议包含目标、类型、方向和可检查依据 |
| 修改后再分析 | 修改正文使旧建议与确认失效；修改关系可更新待提交清单，不静默采用旧结果 |
| 独立入图 | 空库、无匹配或全部拒绝关联时，用户仍可明确确认独立入图 |
| 提交幂等 | 重复点击、断线恢复和工作流重放不会重复生成节点或关系；事务失败不留下部分正式数据 |
| 编辑正文 | 能看到保存状态并恢复历史版本；改名不丢失关系 |
| 对话建边 | 询问不自动建边，明确确认后仅建立预览或回复所指的关系 |
| 关系修改 | 可修正类型、方向与说明，可撤销并查到确认来源 |
| 并发变化 | 确认前正文或端点变化时提示复核；重试不会重复建边 |
| 模型配置 | 对话与向量服务独立测试；错误配置得到明确反馈，密钥不进入导出 |
| 自动聚类 | 使用至少三个领域的样本验证可解释分组；孤立点不会被强制归类，相似度边不会变成正式关系 |
| 配色稳定 | 相同输入重复计算保持稳定；少量新增节点后，未变化云团尽量保持颜色和位置 |
| 三维探索 | 能自由飞行、缩放、聚焦、返回全景；输入文字时不会触发移动 |
| 正文阅读 | 点击节点可展开 Markdown，退出阅读后保留空间位置 |
| 图查询 | 正确区分直接关系、多跳路径、无范围内路径与模型推测 |
| 备份恢复 | 完整导出后在空库恢复，节点、正文、关系方向及确认来源一致 |
| 降级使用 | 模型断开或三维不可用时，仍可编辑知识和手工维护关系 |

建议性能目标：先以 1,000 节点、5,000 条正式边作为首版验证数据集；在约定的桌面设备和浏览器上，默认视图交互帧率目标不低于 30 FPS，已有节点正文打开目标在 1 秒内完成（不含模型请求）。更大数据集使用局部加载和层级细节，具体上限在原型实测后确定。这些是待验证目标。

## 9 实施顺序

1. **需求修订**：明确部署方式、Markdown 文件要求和对话建边规则。
2. **基础闭环**：清理旧项目，完成数据库、草稿与知识编辑、手工关系、导入导出和基础备份。
3. **录入与对话闭环**：接入 LangGraph、模型配置，完成解析、知识匹配、关联建议、人工审阅、确认入图、流程恢复，以及已有节点的对话建边和撤销。
4. **空间闭环**：完成三维导航、节点正文、聚类、配色和稳定布局。
5. **验收调整**：用你的真实知识验证关系表达、分组可解释性、性能和备份恢复。

每一步均应产生可使用和评审的结果；第一版交付应覆盖前三个使用流程，而不是只有演示点云。

## 10 优先讨论的问题

这些问题用于下一轮修改；下表建议值不代表你已经确认。

| 问题 | 当前建议 | 对产品的影响 |
| --- | --- | --- |
| 平时在哪里使用？ | 先在自己的电脑启动、浏览器使用 | 决定是否需要云端部署、账号和同步 |
| 是否必须每个知识点都对应真实 `.md` 文件？ | 先在应用编辑，随时导出 | 若要直接用 IDE 编辑，需设计文件夹同步和冲突处理 |
| 你描述的询问方式是否是“你提问，AI 追问，你确认后连线”？ | 按这个流程设计，也可手工连线 | 若希望 AI 主动访谈，需要增加主动追问入口 |
| 用自然语言明确说“连接”能否直接保存？ | 可以，含糊回答才继续澄清 | 决定是否还要每次点确认按钮 |
| AI 能否写正文和新增知识？ | 首版只建议，由你决定新增或改写 | 决定模型的写入权限和审阅流程 |
| 云团按什么分？ | 按正文语义自动计算，手动标签只用于筛选 | 若希望按关系密度或人工学科划分，应增加模式切换 |
| 更看重初期安装简单，还是未来跨设备扩展？ | 当前先采用 PostgreSQL，保留评估 SQLite 的机会 | 决定首版数据库与部署成本 |
